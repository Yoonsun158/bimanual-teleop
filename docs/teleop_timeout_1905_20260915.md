# 2026-09-15 遥操作目标超时：原因与解决方案

## 结论

附件的 9 次目标超时，直接原因都是：**主机还没有提交下一条双臂命令，上一条命令就已到期。** 双臂反馈和本轮 Quest 输入当时仍有效，没有 IK 求解失败首因。另有 1 次独立的 Quest 坐标系切换暂停。

当前结构对连续两个周期的延迟特别敏感：50 ms 从求解前的目标生成时刻开始，上一轮求解先用掉部分预算，下一轮又要串行求解双臂。因此“距上次提交不到 50 ms”并不代表还有时间。这是现有保守时限契约的结果，不能直接称为 watchdog 误判。

本轮重点研究降低控制线程的等待时间：先验证反馈降频，优先考虑将手部收流、重定向与机械臂控制分进程；不要把加大超时、换求解器或升级 SDK 当作已经证实的修复。

本轮未修改运动代码、时限、设备设置或依赖，未连接设备或下发运动。详细数据见[逐次日志证据](teleop_timeout_1905_evidence_20260915.json)。

### 数据来源

用户本次附件 `c571a14f.../pasted-text.txt` 的内容是此前 `deeff016.../pasted-text.txt` 中 19:05–19:11 段的连续子串；10 条诊断逐字段完全一致。这里是对同批数据的进一步分析，不是新增实机实验。此前 18:59 全段报告有 13 次目标超时，本附件的子集有 9 次，两者不能累加。

9 次中，5 次由后台 watchdog 先发现，4 次由新命令提交时先发现；它们是同一到期条件的两个检查入口。9/9 次双臂求解合计耗时都超过开始求解时旧命令的余量。

这里不能把 57 ms 都叫作 CPU 计算：计时包括线程调度、GIL、锁和原生调用等待；5/9 次计时还跨越了首次停机，可能夹有停止动作的影响。4 次拒绝路径中的 `driver_submit_ns≈19–21 ms` 包含同步 `request_hold → tj_hold`，也不能拿它证明正常发送慢。

Wuji 的 247 条 `Stall` 和 44 条 `Enc1BitRate` 不是这 9 次记录的停机首因。它们带来的接收/日志负载是否间接影响控制线程，仍需完整进程采样验证。手部 ready 是停机后补取的快照，不能据此断言故障瞬间完全没有影响。

## 2. 为什么不到 50 ms 就停

代码链路：

1. [mapping.py](../bimanual_teleop/control/arm/mapping.py) 的 `sample()` 在求解前设置 `expires=min(参与插值的源期限, now+50 ms)`。
2. [cartesian.py](../bimanual_teleop/control/arm/cartesian.py) 的 `submit()` 串行计算左右臂，并保留创建时间和期限。
3. [driver.py](../bimanual_teleop/devices/tianji/driver.py) 的 `_send_command()` 检查上一命令是否已过期；接受新命令时依旧保留其原到期时间。

因此，在源期限未进一步缩短预算时，需要满足：

`上一目标生成 → 上一轮求解/提交 → 周期间工作 → 本轮求解/提交 < 50 ms`

`target_age_ms` 则从上一命令进入驱动开始计算，没有包含上一轮求解。这两个时间的起点不同。

实测例子（附件第 343 行，以旧命令进入驱动为 0）：

| 时刻 | 事件 |
| ---: | --- |
| 0 ms | 旧命令进入驱动 |
| 0.195 ms | 原生调用已返回 |
| 8.479 ms | 生成新目标，其到期时间为 58.479 ms |
| 8.602 ms | 开始求解新目标 |
| 24.676 ms | 旧命令到期 |
| 至少 27.862 ms | 双臂求解完成，合计 19.259 ms |
| 27.967 ms | 提交被拒并记录停止；新目标仍余 30.511 ms |

本例没有计算跨过停机时刻的问题，清楚展示了“旧目标先到期、新目标仍有效”。日志里的 `target_remaining_ns=50000000` 是新目标**生成时**的快照，不能用它判断旧目标。

## 3. 优先检验控制线程等待与争用假设

空载数值测试不能覆盖完整实机接收负载。当前同一 Python 3.10 进程里有机械臂反馈解码、双手状态/诊断解码、Quest 接收与解析、手部重定向、主控制和 watchdog 等线程。Wuji 接收循环每次可连续处理每流 128 帧，机械臂 `_drain()` 每次可处理 256 帧；帧数有上限并不等于墙钟等待有可靠上限。

CPython 的 Python 线程共享 GIL；`ctypes.CDLL` 调用会释放后重新获取它。控制线程短暂调用数值/原生函数时，其他 Python 接收线程可以抢先执行，从而把微小运算之间的等待累积起来。这是需要实测验证的机制，不能仅凭语言特性就确定现场归因。[CPython 线程说明](https://docs.python.org/3.10/library/threading.html)、[ctypes 调用说明](https://docs.python.org/3.10/library/ctypes.html#ctypes.CDLL)。

之前只测双臂加重定向的实验没有完整收流，因此不能用“空载只有 1–4 ms”排除主机延迟。

### 本轮新增离线对照

使用当前真实 M6 运动学和 `CartesianServo`，只改变背景负载，顺序启动独立实验进程。持续占用 Python 的负载用同一函数分别放在同进程线程和另一个进程中。

| 条件 | 双臂样本数 | 双臂墙钟中位数 / P99 | 双臂线程 CPU 中位数 | 超过 50 ms |
| --- | ---: | ---: | ---: | ---: |
| 空载 | 1500 | 1.407 / 2.456 ms | 1.407 ms | 0 |
| 同进程持续 Python 忙线程 | 100 | 64.937 / 90.908 ms | 4.532 ms | 93 |
| 相同忙负载移到独立进程 | 1500 | 1.591 / 2.686 ms | 1.591 ms | 0 |
| 合成 1 kHz 臂反馈 + 每手 1 kHz 状态/诊断 | 3000 | 2.885 / 7.481 ms | 1.799 ms | 0 |
| 臂反馈不变，每手状态/诊断改为 200 Hz | 3000 | 2.672 / 6.428 ms | 1.944 ms | 0 |

忙线程组运行约 6.49 秒，最大双臂墙钟 92.726 ms；双臂线程 CPU 的 P99 仅 6.266 ms。**该机制实验重现了“计算线程自身用时很少，墙钟却超过 50 ms”；同样负载分进程后明显缓解。** 它支持优先隔离同一解释器内的竞争，但不证明现场正好存在这个强度的忙线程。

分段时间也吻合这种解释：忙线程下 FK、Jacobian、伪逆、SVD、QP 的墙钟中位数落在约 5.16–5.30 ms，而对应线程 CPU 只有约 0.10–0.23 ms，接近当前 5 ms 的 Python 切换间隔。忙线程组最大垃圾回收仅 0.063 ms；独立忙进程实际仍消耗约 2.50 秒 CPU/2.50 秒墙钟，改善并非因为取消了背景负载。

反馈组降至 200 Hz 后 P99 有小幅改善，不能称为根治。同样的合成 1 kHz 反馈条件下，将 Python 切换间隔从 5 ms 改为 1 ms，P99 为 15.027 ms；BLAS 改为单线程后 P99 为 10.561 ms。本轮都没有显示优于原设置的稳定收益，因此不据此修改默认值。

实验限制：固定初始关节和 3/2/1 mm 小位移目标，左右速度/加速度比例均为 100%（实机右臂为 15%）；不调用 `accept()` 推进状态，也不按 200 Hz 休眠。反馈组只用合成对象走实际 Python 接收/解码代码，不包含原生 SDK 属性访问、Quest 解析、手部重定向或停机回调。它们均没有重现超过 50 ms 的反馈负载延迟。QP 在这些固定目标中最多 3 轮，但这不能排除现场其他姿态的难例。计时包装有开销，保留正常垃圾回收并记录其耗时；各组在共享工作站顺序执行且样本量不同，不能把某个最大值/P99当作稳定的性能排序。

完整方法、CPU/墙钟分段、收流数和源码指纹见[新增实验 JSON](teleop_servo_latency_additional_20260915.json)；历史实验脚本路径为 `docs/experiments/servo_latency_20260915.py`（已退役）。表中的忙线程和忙进程数据分别来自当时的 `busy 100`、`process_busy 1500` 离线实验；原始记录与源码指纹保留。

## 4. 解决方案与实施顺序

### 第一阶段：对完整负载做可归因的减负验证

**首选验证 Wuji 反馈从默认满速降低至 200 Hz，同时保持机械臂控制率和保护期限。** 官方确认 Hand 2 状态原生输出为 1000 Hz，状态与诊断共享设备流；`Subscription.set_rate(200)` 返回实际频率。当前项目订阅两流但没有设置频率，当前安装的 `wuji-sdk==2026.8.31` 已确认有此方法。固件要求 Hand 2 v2.3.0 或更新版本，设备实际固件本轮未读取。[官方接口说明](https://docs.wuji.tech/docs/en/wuji-hand/latest/sdk-reference/#adjusting-the-stream-output-rate)、[官方版本记录](https://github.com/wuji-technology/wuji-sdk/blob/main/CHANGELOG.md#2026817)。

这里的 200 Hz 是建议的对照起点，不是已验证的生产参数。设置作用于共享设备流，最后写入者生效，最后订阅关闭/重连会恢复默认；必须保存返回的实际频率，不能分别要求状态 200 Hz、诊断 100 Hz。降频也改变故障观察时间分辨率，应验证短暂故障/离线/停手行为；不能仅在 Python 中丢掉诊断帧来减负。

同时在停机前保留有限长度环形记录：每阶段墙钟和当前线程 CPU、旧目标余量、源期限、收流数量和批次耗时。只在暂停后序列化。结合进程及原生工作线程的 CPU 判断：当前线程 CPU 不包含 BLAS 等工作线程，低线程 CPU 不能单独排除并行数值计算。CPU 随墙钟一起升高通常优先检查计算；墙钟升高而相关线程 CPU 很低则优先检查等待。单次停机快照不能代替前面连续周期的记录。

### 第二阶段：隔离争用，改善持续周期

**优先将手部接收、重定向及日志放入独立进程，机械臂控制独立运行。** 同进程再加求解线程不能消除共享 GIL；分进程的收益必须在同样轨迹和完整收流条件下验证。进程间传递带原始序号、时间、期限的最新快照，避免 FIFO 积压后回放旧动作。暂停、子进程退出、故障锁存和显式重新接合必须保持一致。

更长期可将机械臂周期求解、发送和停止监督放入原生固定周期循环，预分配内存、限制等待，将界面和日志移出控制路径。CPU 亲和、实时调度和内存锁定应在实测调度问题后配套使用，避免高优先级循环饿死反馈。可以采用这些原则，无需为了它们整体迁入 ROS。[ros2_control 确定性说明](https://control.ros.org/jazzy/doc/ros2_control/controller_manager/doc/userdoc.html#determinism)。

### 不应直接作为修复的改动

- **延长 watchdog／提交时重新给目标 50 ms：** 会扩大陈旧规划结果的容忍时间，不能消除控制周期抖动。源输入期限、规划结果最大年龄和提交间隔可以拆分设计，但属于行为变更；“提交时输入新鲜”不等于关节解使用了那份新输入。重复发送旧目标也不能无限续期。
- **强制 BLAS 单线程／缩短 Python 切换间隔：** 可以做单变量对照，当前证据不支持稳定有效。NumPy 的 BLAS 后端可能多线程，但必须核实实际构建及线程数，不能只设置环境变量就认为已生效。[NumPy 说明](https://numpy.org/doc/stable/reference/global_state.html)、[OpenBLAS 运行时变量](https://www.openmathlib.org/OpenBLAS/docs/runtime_variables/)。
- **直接更换 QP 求解器：** OSQP 有 `time_limit/max_iter`，qpOASES 有 `nWSR/cputime`，但预算不包含 Python 前后处理，也不是系统调度保证。现有日志没有证实 QP 难例；换求解器还需重新验证边界数值、约束及连续性。若将来采用有预算求解，预算不足时只能执行经过验证的合法减速退路。[OSQP 设置](https://osqp.org/docs/interfaces/solver_settings.html)、[qpOASES 接口](https://coin-or.github.io/qpOASES/doc/3.0/doxygen/classQProblem.html)。
- **直接升级 Wuji SDK：** 2026.9.14 确实修复了同应用共享多设备读写超时和部分 `sdk_dropped` 漏计，但本次首因来自项目 Tianji watchdog，不能等同。新版还包含异常类型和关节编号接口等不兼容变更，应独立核验后迁移；使用 `set_rate` 不必先升级当前 SDK。[官方更新记录](https://github.com/wuji-technology/wuji-sdk/blob/main/CHANGELOG.md#2026914)。
