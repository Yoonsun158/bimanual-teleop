## 已复现并修复的并发问题

### 1. watchdog 使用过期判断误停新命令

旧代码在驱动命令锁之外读取时间和期限，然后进入 `request_hold()` 等待同一把锁。新提交可以在等待期间成功更新期限，监控线程却仍执行旧判断。

固定时钟、真实线程交错、假原生发送的复现：

1. 旧目标在 50 ms 到期；新提交在 49 ms 进入原生调用。
2. watchdog 在 51 ms 读到旧期限，准备停机并等待命令锁。
3. 提交在 52 ms 成功，期限已变为 99 ms。
4. 旧实现仍停机，出现 `accepted=True` 与 `engaged=False`。

现在检查时间、接合状态、期限和执行停机使用同一临界区；完全相同的交错保持接合。真实到期、反馈超时、控制器错误和发送故障继续触发停止，没有增加期限。

### 2. 状态查询等待手部求解锁

调用链是 CLI 每秒状态查询 → 联合运行时状态 → `WujiTeleop.status()` → 手部控制锁。手工作线程持有这把锁执行官方重定向与发送，因此查询状态也会等待设备工作完成。

旧实现给假重定向注入 80 ms 等待（释放 GIL），状态查询阻塞约 81.1 ms，而同次轻量健康检查约 0.020 ms。机械臂命令期限为 50 ms，这条等待路径能独立制造同类超时。

现在状态查询读取完成周期的内存快照；主线程健康检查直接检查接收样本、诊断样本的有效性／原有新鲜度阈值，以及已锁存错误。SDK 连接和用户查询由手部工作线程执行，接合时同步重新核验。未增加新的手部 50 ms 超时判据。

相同 80 ms 故障注入下，修改后状态查询约 **0.125 ms** 返回，此时手部工作线程仍在等待。SDK 健康观察使用既有 `hand_timeout_s`（默认 500 ms）作为有效期限：设备反馈持续到达也不能让已卡住的工作线程无限报告正常。该期限针对缓存检查结果，不是新增 50 ms 手部指令 watchdog。

联合暂停先向机械臂请求停止，再在 `finally` 中暂停手部，避免停臂请求先等待手部工作锁。

## 排除未经证明的计算优化

双臂速度求解 200 Hz 与官方 `RetargetSession` 双手 120 Hz 并发，使用本地运动学和重定向，不创建 Manager、不连接设备。对照原实现、三角求解替换、BLAS 单线程及二者组合，各运行约 15 秒。

原实现双臂计算中位数／P99／最大耗时约 **1.574／3.314／4.074 ms**。四组共约 12,000 个双臂周期没有一次计算超过 20 ms。单线程和三角替换并未稳定改善尾延迟，因此保留现有数值实现。共享工作站的离线实验不能证明实机进程永远不会被调度延迟。

数据、源码标识和实验条件见 [计算时延对照记录](teleop_pause_numeric_latency_20260915.json)。正常笛卡尔提交也不调用 Python `_wait_sent()` 等待控制器 ACK；它是异步发送，SDK 返回与机器人实际执行仍有区别。

## 新增故障证据

自动暂停输出一条 `[停机诊断]` JSON：

- `driver_stop`：首次原因、单调时间、上一命令及其期限、超期量、双臂反馈源计数推进年龄、最近原生调用耗时。SDK 停止成功和上层重复暂停均不抹掉首因。
- `cycle`：相邻 tick 间隔、输入检查、反馈 FK、映射、执行器耗时、输入接收年龄，以及输入／插值目标的剩余有效时间。刚收到数据不等于源数据新鲜。
- `executor`：左右臂各自计算、驱动提交耗时及当前命令时间。
- `host_loop`：进入控制前的工作、最近状态查询、键盘等待和唤醒迟到。最近状态查询带时间戳，不能将很久之前的慢查询直接归因到当前暂停。
- `hands`：联合模式下，手部最近完成周期的耗时、完成时间、年龄和已观测的 SDK 用户健康状态。记录时点是暂停报告时，不能替代最初故障时刻。

这些时间用于区分“输入排队、计算慢、设备调用慢、状态查询慢、主线程被延迟调度”；它们不是网络单程时延或控制器执行确认。只在异常时序列化输出，每周期仅更新有限个时间字段。
