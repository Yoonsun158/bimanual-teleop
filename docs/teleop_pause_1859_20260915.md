## 1. 超时如何发生

当前代码在求解前生成目标，期限为 `min(源数据期限, 生成时刻 + 50 ms)`；然后串行计算左右臂。驱动保留该期限，并要求上一条命令尚未到期，才允许下一条提交。

代码位置：

- `control/arm/mapping.py:315`：生成目标及其到期时间。
- `control/arm/cartesian.py:143`：左右臂串行 `servo.propose()`；179 行起保留原创建时间和期限。
- `devices/tianji/driver.py:891`：提交前检查旧命令期限；904 行确定新 deadline。
- `devices/tianji/driver.py:594`：后台 watchdog 检查同一期限；947 行的 `target_age_ms` 从驱动提交开始计时，不含前面的求解时间。

因此连续两轮求解和其间工作都需要赶在旧目标到期前完成。例如，离线用真 TianjiDriver 和假原生设备复现：

| 相对时刻 | 事件 |
| ---: | --- |
| 0 ms | 旧目标生成，期限为 50 ms |
| 24 ms | 旧目标进入驱动并获接受，剩余 26 ms |
| 30 ms | 新目标生成，期限为 80 ms |
| 53 ms | 新目标尝试提交：自身剩余 27 ms，但旧目标已过期 3 ms |

结果正确拒绝为 `Previous target watchdog expired`，旧目标 `target_age_ms=29`。这解释了日志中“目标年龄不到 50 ms 却已经超时”的现象。

两个英文原因是同一机制的不同检测入口：提交线程先发现则报 `Previous target watchdog expired`（5 次）；后台线程先发现则报 `Accepted target expired...`（8 次）。日志中的 `target_remaining_ns=50000000` 属于当前新目标刚生成时的快照，不能拿它判断上一条目标是否到期。

## 4. 性能定位与验证边界

同一工作树、本地厂家运动学、合成目标及反馈，使用 Conda `bimanual-teleop` 进行无设备对照；具体条件和统计在证据 JSON 中。该实验没有实机失败时的关节/目标轨迹、原生设备订阅或完整现场负载，不能等同于逐帧重放。

每组重复 1000 次固定参考姿态和固定小位移目标的 `propose()`，不调用 `accept()` 推进状态，主测试循环连续运行，不按 200 Hz 休眠：

| 条件 | 双臂中位数 | P99 | 最大 |
| --- | ---: | ---: | ---: |
| 无接收线程，默认 BLAS | 1.289 ms | 1.541 ms | 1.860 ms |
| 无接收线程，BLAS 单线程 | 1.146 ms | 1.326 ms | 1.444 ms |
| 加入模拟 1 kHz 机械臂反馈 | 2.403 ms | 5.370 ms | 23.973 ms |
| 再加双手，每手 500 Hz 状态、100 Hz 诊断 | 2.465 ms | 5.215 ms | 15.857 ms |
| 双手各改为 1 kHz 状态和 1 kHz 诊断 | 2.958 ms | 6.829 ms | 16.139 ms |

模拟接收调用实际 Python `_receive/_drain/_on_feedback` 或 Wuji 接收/解码流程，但使用合成对象，不包含原生 SDK 属性访问、Quest 解析、手部重定向、实际通信或停机回调。Wuji 频率是实验假设，不是设备实测。各组在共享工作站顺序执行，最大值不能直接当作稳定的性能排序。

空载 QP 单次中位数约 0.024 ms。受压组出现单臂墙钟最大 14.65 ms、线程 CPU 时间最大仅 2.28 ms 的现象，支持存在等待或调度延迟。接收线程确实能拉长时间；上述组都没有完整重现日志的极端延迟，也没有证明单线程 BLAS 可以解决实机中断。

Python 3.10 的多个线程共享 GIL，`ctypes.CDLL` 调用会释放并重新获取它；当前 FK/Jacobian 路径有这种交接。因此接收线程与数值计算间的争用是优先检查项。这个机制由 [CPython 线程文档](https://docs.python.org/3.10/library/threading.html)和 [ctypes 文档](https://docs.python.org/3.10/library/ctypes.html)支持；[CPython issue #52194](https://github.com/python/cpython/issues/52194)记录过类似等待放大现象，但不是本项目根因已被证明的依据。

上次数值基准只有双臂计算加双手重定向，没有设备接收负载；现有时序回归又使用假时钟。它们能验证控制约束或时间语义，不能证明真实多线程运行持续满足 5 ms 周期和 50 ms 期限。

本轮 watchdog 与停机诊断定向回归共 **11 项通过**，`git diff --check` 通过。该结果确认当前语义和诊断行为，没有证明实机时延问题已解决。

## 5. 下一步应查什么

优先对完整进程采集“墙钟时间 + 当前线程 CPU 时间”，保留停机前若干周期的环形记录，并细分 FK、Jacobian、矩阵分解、QP 和提交前等待；同时记录各接收线程处理帧数、批次耗时与排队情况。这样可以直接区分“函数真正计算变慢”与“主线程在等执行机会”，并避免把停机后的耗时算成起因。

若确认接收/GIL争用，应优先隔离接收负载与机械臂控制周期；若 CPU 时间也同步升高，再定位并优化具体运算。现有证据不足以直接决定换求解器、改 BLAS 线程数或放宽 watchdog。单纯延长命令期限不能修复控制周期抖动。
