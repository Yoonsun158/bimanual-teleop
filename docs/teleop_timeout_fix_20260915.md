# 2026-09-15 遥操作超时：根因修复与实测

## 结论

已复现的主要问题是：Wuji 高频收流、重定向与机械臂周期计算运行在同一个 Python 解释器里，争用 GIL，把短计算拉长为数十毫秒。删除冗余查询后，同进程实测仍出现一次双臂计算 **70.50 ms**、该线程自身 CPU 用时仅 **5.79 ms**。因此，本次将完整手部运行时移入独立进程，直接消除它与机械臂计算之间的解释器争用。

日志里的直接停机条件是上一条机械臂命令先到期：50 ms 从目标生成开始计时，包含上一轮求解和下一轮提交前的间隔。9 次日志超时均符合这个时序，另有一次独立的 Quest 参考系切换。逐次证据见[原始日志分析](teleop_timeout_1905_20260915.md)。

CPython 3.10 的 Python 线程共享 GIL，`ctypes.CDLL` 调用释放后需要重新获取它；同一周期内多次短原生调用可以累计多次等待。[Python 线程说明](https://docs.python.org/3.10/library/threading.html)、[ctypes 说明](https://docs.python.org/3.10/library/ctypes.html#ctypes.CDLL)。此前受控实验把同一 CPU 负载从线程搬到进程后，双臂计算中位数从 64.94 ms 降到 1.59 ms，支持上述机制；本次进一步使用实际手套、Hand2 和机械臂反馈验证。

## 实际代码变化

### 1. 完整隔离手部工作

联合模式的 [CLI](../bimanual_teleop/cli/teleop_quest_tianji.py) 创建 [WujiProcess](../bimanual_teleop/control/hand/process.py)。子进程使用 `spawn`，自行创建 SDK manager、四个设备、接收线程、重定向器及 120 Hz 手部控制线程。主进程负责 Quest 和机械臂。

进程间只发送生命周期请求和 50 Hz 观察快照，包含手势所需的原始骨架样本及健康状态；手部关节命令不经过主进程，1 kHz 反馈不逐帧跨进程转发。快照保留原始序号、epoch 和接收时间。骨架、关节、诊断和工作线程各自的过期时间仍有效，收到新快照不延长旧数据的寿命。

暂停使未完成的接合失效；恢复须重新接合。父进程失联时子进程暂停，子进程失联时主进程健康检查失败。生命周期操作与跟随工作共用已有的取消代际，避免暂停后迟到的准备结果重新接合。

### 2. 删除不参与控制决策的热路径工作

- **Wuji：**删除每个双手周期 1 次 `current_user()` 和 14 次 `is_connected` 查询，即名义 120 Hz 下约 1,800 次 SDK 查询/秒；用户检查保留在启动及准备接合。删除配套轮询缓存、TTL 和重复健康入口。
- **Wuji：**无记录器时仅订阅 skeleton，删除控制未使用的 EMF 收流与解码；显式记录器路径仍保留原始溯源。诊断状态字每关节取一次，固定错误码等级复用，避免重复原生属性查询。
- **机械臂：**反馈每包分类一次，驱动集中持有硬件故障状态；删除 runtime 的重复分类。无记录器时参数信息改为显式读取 metadata 时构造。
- **机械臂：**删除每周期两次实际反馈 FK。这两次结果只用于重复检查静态坐标系名称；每个双臂周期从六次 FK 减为求解必需的四次，参考姿态仍在接合时建立。

原启动命令不变：`python scripts/teleop_quest_tianji.py`。手部仍为 120 Hz，机械臂目标仍为 200 Hz。机械臂命令期限仍为 50 ms，Quest 新鲜度仍为 100 ms。没有升级 SDK、修改 GIL 间隔、延长超时或降采样诊断反馈。

### 验证边界

这些计数中的“超时”是 `前后周期起点间隔 + 本轮双臂计算时间 >= 50 ms` 的离线判据，用来对照旧命令期限；不是实际控制器停机次数。计时包含线程调度和 GIL 等待。探针额外包装部分接收函数计时，阶段累计统计包含启动阶段；表格的周期统计仅覆盖设备准备完成后的测量区间。

本次没有使能设备、配置运动参数或提交机械臂/手部运动命令。机械臂 SDK 的现有连接初始化包含 `LOGOF=0`（关闭控制器日志）及 VERSION 查询，因此涉及机械臂连接的测试不称为严格的纯读操作。

当前验证不包含 Quest 实际 UDP 输入、全身实动、实际姿态变化或运动发送负载。已复现并处理的是主机争用造成的延迟；有限时长采集不能证明所有工作负载下永不超时，真实输入中断和控制器故障仍应暂停。
